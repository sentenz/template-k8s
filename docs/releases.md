# Releases

Semantic Release validates main before calculating a stable version. Its GitHub
App token pushes the release commit and numeric tag and creates the GitHub Release.
The release commit deliberately has no `[skip ci]` marker: tag pushes must run CI.
The resulting extra branch run validates the release commit; `chore(release)` does
not itself request another version under the Conventional Commits preset.

The tag-triggered Release workflow checks strict SemVer, tag/commit agreement and
main ancestry, then reruns policy, security and Kind validation on the tagged
commit. It publishes a versioned multi-platform image with explicit max provenance
and an image SBOM, signs its digest, generates/scans/signs source SBOMs and archives,
and uploads assets to the existing GitHub Release. Asset upload waits up to five
minutes for Semantic Release and never creates a competing release.

Only after these jobs succeed may a serialized job promote that digest to `latest`.
It checks all stable Git tags using numeric version ordering inside the lock. An
old-version rerun cannot replace a newer release. A higher tag whose build fails
blocks lower-version promotion; recover that higher release rather than moving tags.
The GitHub Release and versioned image can be visible before every job completes;
this is not an atomic publication transaction.

## Configuration before merging

Install a dedicated GitHub App on this repository with Contents, Issues and Pull
requests read/write permissions, plus Workflows write permission to push tags
whose commits contain workflow changes. Configure repository variable
`RELEASE_APP_ID` and secret `RELEASE_APP_PRIVATE_KEY`. The token action limits each
installation token to the current repository. No PAT or GITHUB_TOKEN fallback is
used: a fallback would silently suppress the downstream tag workflow.

Protect main with required PR checks and protect numeric release tags against
updates/deletion and unauthorized creation. Main ancestry is checked in code but
is not a substitute for tag creation rules. Maintain action SHA pins through the
existing dependency automation.

## Recovery and verification

Rerun the failed Release run, or dispatch release.yml with an existing release tag
as its selected ref (`gh workflow run release.yml --ref 1.2.3`). Dispatching main
does not publish. For asset-only recovery, dispatch sbom.yml with both its ref and
version set to the same tag. Never move a release tag to repair a failed run.
Reruns can rebuild/replace the versioned image and source assets; consumers should
pin and verify image digests.

Sigstore identities now use the tag and called workflow path:

- `https://github.com/sentenz/template-k8s/.github/workflows/docker.yml@refs/tags/1.2.3`
- `https://github.com/sentenz/template-k8s/.github/workflows/sbom.yml@refs/tags/1.2.3`

Update consumer verification policies before the first release. Check the first
real release's source SHA and ref in its provenance, verify the image and file
signatures with the exact identity and GitHub issuer, and confirm both architectures
and all release assets are available. Source SBOM signatures do not constitute
build provenance; image provenance and image SBOMs are generated by BuildKit.
