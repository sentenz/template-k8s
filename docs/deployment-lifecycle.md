# Deployment lifecycle

## Ownership and topology

This repository uses Helm as a template renderer inside Kustomize. `make k8s-deploy` applies the rendered Kubernetes objects with `kubectl apply`; it does not install a Helm release. There is no Helm revision history, automatic Helm rollback, or Helm hook execution lifecycle. A `releaseName` in a Kustomization controls template naming only.

One distinct cluster is assumed for each of `dev`, `stage`, and `prod`. The environment roots reuse namespace names and cluster-scoped resource identities. Applying two roots to the same cluster would modify overlapping objects. A shared-cluster design requires explicit namespace isolation and one owner for cluster-scoped resources before deployment.

Application configuration belongs in `apps/`, independently managed platform capabilities in `platform/`, and concrete target composition in `clusters/`. Namespaces currently belong to capability bases. The aggregate destroy command consequently deletes those namespaces and all namespaced contents; it is not an application-only uninstall command.

## Validation and apply

```bash
make helm-vendor-check
make k8s-render K8S_ENV=stage
make k8s-render-check K8S_ENV=stage
make k8s-deploy K8S_ENV=stage
```

Rendering development requires local TLS fixture files, generated by the certificate workflow or supplied through the documented encrypted fixtures. CI generates disposable certificates instead of decrypting committed fixtures.

The manifest CI matrix renders all environments through the same Make target and pinned tools image used locally. Vendoring and validation tasks are implemented in the Makefile and use containerized Helm, yq, jq, and kubeconform without a host Python dependency. Validation checks vendored references, Kubernetes schemas, unique resource identities, environment labels, and expected Traefik networking. The Kind workflow also deploys the development composition and checks workload readiness and ingress endpoints.

`kubectl apply` acceptance does not establish application readiness. Production automation must wait for relevant workloads and application health checks. Entries in `resources:` do not establish readiness ordering. If controllers and dependent custom resources are introduced, install controllers and CRDs, wait for readiness, and then apply their configuration in explicit phases.

Rendered manifests can contain Secrets. Keep them out of Git and public CI artifacts, restrict access, and remove them when validation is complete. Schema checks do not replace admission checks against the intended cluster.

## Promotion and dependencies

Add a new chart version with `make helm-vendor`; it preserves existing versions and rejects overwriting immutable directories. Update the development overlay first, validate it, and then promote the same chart and image references to stage and production. Retain all chart versions still referenced by any overlay. Preserve environment-specific hostnames, credentials, and sizing during promotion.

Third-party charts can generate hooks or depend on Helm lifecycle behavior. Review those resources before chart upgrades: applying an annotated Job through kubectl does not implement Helm hook ordering, cleanup, or rerun behavior. Changed immutable Job fields may require a deliberately managed replacement.

## Removal and rollback

Plain `kubectl apply` does not remove resources omitted from a later render. Resource removal needs an explicit, reviewed inventory or a controller that owns pruning. Do not use the aggregate `k8s-destroy` command to remove one application; it includes platform resources and namespaces.

Rollback restores a known-good Git configuration and retained chart/image versions, renders it, and reapplies it. It cannot use `helm rollback` because no Helm release was installed. Compare resource inventories when reverting, handle immutable-field changes explicitly, and verify workload and application health afterward.

Manifest rollback does not restore database contents, external Secrets, or other external state. Database migration compatibility and backup recovery remain separate operational responsibilities.

## Future GitOps integration

The cluster directories can become reconciliation roots, but this repository does not configure a GitOps controller. Choose one owner for each resource. A future HelmRelease-based workflow changes release ownership and must migrate resources deliberately rather than run alongside kubectl management of the same objects.
